# NoSQL Justification Report — FlexiMart (MongoDB)

## Section A: Limitations of RDBMS (≈150 words)
A relational design works best when every row in a table shares the same fixed columns. With a diverse product catalog, products don’t share the same attributes (e.g., laptops need RAM/CPU/storage while shoes need size/color/material). In MySQL, you either (1) add many nullable columns to a single `products` table (wasting space, messy validation), or (2) create multiple subtype tables (more joins, more complexity). When new product types arrive frequently, schema migrations become continuous work: ALTER TABLE operations, backfills, deployment coordination, and versioning of application code. Storing customer reviews as nested data is also awkward in pure relational form: reviews must live in a separate table, requiring joins for every “product + reviews” read, and making it harder to fetch a complete product document efficiently. These issues increase development overhead and can slow queries as joins and schema changes grow.

## Section B: NoSQL Benefits (≈150 words)
MongoDB fits heterogeneous product data because each product is a JSON-like document and can store only the fields it needs. This flexible schema lets FlexiMart add new attributes or new product types without altering a global table definition—application logic can evolve gradually while old documents remain valid. MongoDB also supports embedded documents and arrays, so reviews can live inside the product document (e.g., `reviews: [{user, rating, comment, date}]`). That makes “show product details with reviews” a single read without joins, which is great for catalog pages. For growth, MongoDB supports horizontal scalability via sharding: data can be distributed across multiple machines by a shard key (like `category` or `product_id`) to handle larger catalogs and higher traffic. Replication (replica sets) improves availability and read scaling for common catalog queries. Overall, MongoDB reduces schema friction while matching the natural shape of product + specs + reviews.

## Section C: Trade-offs (≈100 words)
Two disadvantages versus MySQL are:  
1) **Weaker multi-document transaction needs / relational constraints**: while MongoDB supports transactions, enforcing strict relational integrity (foreign keys, complex constraints) across many collections is more natural in MySQL. If FlexiMart later needs heavy cross-entity consistency, MongoDB requires more application-side enforcement.  
2) **Querying and analytics complexity for highly relational reporting**: deep joins and complex reporting across many entities can be simpler and faster in SQL systems. Aggregations exist in MongoDB, but reporting workflows, ad‑hoc BI, and standardized SQL tooling often remain stronger in relational warehouses/databases.
